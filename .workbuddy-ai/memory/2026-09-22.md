### API facts discovered (important, not obvious from Swagger)
- Every response uses an envelope `{success, message, data}`; errors use
  `{success:false, message, errors:{field:[msg]}, status_code}`.
  BUT list endpoints return a raw DRF page `{count, next, previous, results}`.
- `send-otp` with `purpose=forgot_password` (or `password_change`) returns
  HTTP 400 `حساب کاربری با این شماره یافت نشد` for unknown numbers and 200 for
  known ones → **this is the only way to detect whether a phone has an account**.
  `login-password` also reveals it (`حساب کاربری با این شماره وجود ندارد`) but
  was rejected as a probe (would send a fake password → lock-out risk).
- `PurposeEnum` = login, registration, password_change, auth, register,
  forgot_password, verify.
- The DB currently has **no users**, so the "account exists" branch could not be
  tested end-to-end. `AuthSession.fromResponse` therefore walks the payload and
  picks the first plausible token/user instead of assuming one shape.
- `send-otp` normalises `09123456789` → `+989123456789`.

### Behaviour decisions (flag these if the user disagrees)
- `AppConfig.autoLoginWithSavedToken = true` → with a stored JWT the splash goes
  straight to `MainBottomNavigation` instead of the login screen.
- VPN is a **non-blocking** warning on the splash (auto-continue after 7 s),
  `blockOnVpn = false`. Detection = network interfaces (`tun0`, `ppp0`, `utun4`, …)
  + best-effort public-IP country via a **separate** Dio client (never leak the JWT).
- Splash duration is network-driven: it awaits `GET v1/banners/hero/active/`
  with min 1.5 s / max 12 s.
- Removed the default Flutter launch screen: Android `launch_background.xml`
  (+ `values-v31` for the Android 12 splash, transparent icon) and iOS
  `LaunchScreen.storyboard` now use `#FFF8F0`.
- Probe results cached 12 h per phone (`_AccountProbeCache`) so the probe SMS is
  not sent on every login attempt.

### Gotchas hit
- Batching several `Edit` calls to the **same** file in one message silently lost
  the edits — apply same-file edits one message at a time, or rewrite the file.
- `DioExceptionType.transformTimeout` must be handled (Dio 5.11, non-exhaustive
  switch error).
- `MaterialApp` must not have both `home:` and a `routes['/']` entry (assertion).

## Follow-up audit — `RemoteCache` was dead code (same day)

A self-audit found that `RemoteCache` and `AppConfig.catalogueCacheTtl` were
declared and documented but **never called**, so the switch silently did nothing.
Wired it up with an opt-in policy rather than removing it.

### Policy (important — easy to get wrong)
Cache **public reads only**; anything account-specific must always hit the
network, because a stale `is_enrolled` / `is_favorite` outlives the action that
changed it.

- **Cached:** course lists (featured/latest/free/paid/best_selling), categories,
  `course-detail:{id}`, `lesson:{id}`, `chapter:{id}`, `recipe:{id}`, explore
  reels, teacher portfolio (both cached *after* media hydration), teachers.
- **Never cached:** `fetchEnrollments`, `fetchMyCourses`, `fetchMyFavorites`,
  `fetchCourseProgress`, `fetchReviews`, profile, and `fetchCoursePage` (search —
  one entry per query string is not worth the memory).
- **Invalidation:** `markLesson` + `toggleFavorite` → `RemoteCache.clear()`;
  `submitReview` → `invalidate('course-detail:')`; `registerRecipeView` →
  `invalidate('recipe:')`; `SessionManager.save()` + `.clear()` → `clear()`.
- **The trap:** `_courses(path)` is shared by the public `courses/featured/` and
  the auth `courses/my_courses/`. It now takes `cache: true` by default with the
  two auth callers passing `cache: false` — otherwise one user's course list gets
  cached and served to another.
- New: `RemoteCache.invalidate(prefix)` and `@visibleForTesting RemoteCache.length`.

### Verification
- `flutter analyze` → 131 issues, **0 errors, 0 warnings**
- `flutter test` → **54/54 pass** (46 + 8 new `RemoteCache` tests)
- `flutter build apk --debug` → **built successfully** (96.8 s)

### Lesson
Documenting a config switch as working is not the same as wiring it. Grep for the
symbol (`grep -rn "RemoteCache" lib/`) before believing your own docs.

### Follow-on bug the cache introduced: pull-to-refresh went dead
`RefreshIndicator` calls the same `_load()` as `initState`, so with the cache on
it returned the cached rows and the gesture appeared broken for up to 5 minutes.

Fix: `RemoteLoader.list/value` gained a `refresh` flag that calls
`RemoteCache.clear()` before fetching.

| Screen | `_load` | `onRefresh` |
|---|---|---|
| `CoursesScreen` | `_load({bool refresh = false})` | `() => _load(refresh: true)` |
| `HomeScreen` | `_load({bool refresh = false})` | `() => _load(refresh: true)` |
| `ProfileScreen` | `_load()` — profile is never cached | `_load` |

Note `_applyFilters` in `CoursesScreen` is unaffected: `fetchCoursePage` goes
through the uncached `_page`, so filter/search queries always hit the network.

### Tests added (now 62 total)
- 8 `RemoteCache` tests (round-trip, type mismatch, null, prefix invalidate,
  unknown prefix, clear, remove).
- 8 `RemoteLoader` tests — the seed-fallback mechanism was documented but had
  **no tests** until now: success, failure → seed, empty page → seed, empty seed
  stays empty, `refresh` clears the cache, no-`refresh` keeps it, `value`
  fallback, `action` never throws.

### Verification (final)
- `flutter analyze` → 131 issues, **0 errors, 0 warnings**
- `flutter test` → **62/62 pass**
- `flutter build apk --debug` → built successfully

### Lesson 2
Adding a cache is a behaviour change, not just a performance change. Audit every
caller of the cached method for the "explicit user retry" path — a refresh button
and a background load must not share a cache policy.

## Enrollment / payment investigation (same day)

Went after the one knowingly-fake thing left: «ثبت نام دوره» flipping `isStudent`
locally. My earlier note said "no enrollment endpoint, `v1/payments/orders/` is
the only path" — **that was incomplete**. Re-read the schema properly.

### What the schema actually says
- `v1/courses/enrollments/` really is **GET-only** — no `POST`.
- `OrderCreate` = `{coupon_code, gateway, description, course_ids}`.
  **`course_ids` is `array<integer>`** → an order can be created straight from a
  course id. **No cart step needed.**
- `gateway` enum = `mock | zarinpal | idpay | other`, **default `mock`**.
- `PaymentStatusEnum` = `pending | success | failed | canceled | refunded`.
- Real flow: `POST orders/ {course_ids:[id]}` → pay → `verify_mock` → the
  enrollment appears in `GET courses/enrollments/`.
- `OrderDetail` has `items[]` + `payments` but **no `payment_url`**.
- `OrderItem` exposes **no course id** — only `course_title`, `unit_price`,
  `quantity`, `discount_per_item`, `line_total`.

### Bug found and fixed in existing code
`ShopRepository.createOrder` sent `{gateway, address_id, note}`. Neither
`address_id` nor `note` exists on `OrderCreate`, and **`course_ids` was missing**
— it could only ever have produced an empty order. Rewritten to
`{gateway, course_ids, coupon_code?, description?}`. It had **no callers**, so
nothing regressed.

Also added to `ApiConfig`: `paymentsMockGateway`, `paymentsVerifyMock`.
Added to `support_repository.dart`: `PaymentGateway` + `PaymentStatus` constant
classes (from the schema enums).

### Deliberately NOT written: the payment step
`POST v1/payments/payments/mock_gateway/` returns the identical
`404 شناسه پرداخت یافت نشد` for **every** body tried — `{}`, `{payment}`,
`{payment_id}`, `{id}`, `{authority}`, `{order_id}`, `{order, amount}` — because
the DB has no payments, so the lookup fails before the body is validated. And the
schema types the request body as `Payment`, a *response* schema (DRF quirk).

So `payWithMockGateway` / `verifyMockPayment` were **removed rather than
guessed** — a guessed body is exactly the bug just fixed above. A comment block
in `ShopRepository` records what to probe once a test account exists.

**To finish enrollment:** create a user + order against a test account, POST
`mock_gateway` with one candidate body, read the response, then add the method
with the verified field name.

### Lesson 3
When a probe returns the *same* error for every candidate, you have learned
nothing — stop and document the gap. Guessing a request body is how the
`createOrder` bug happened in the first place.

## Live smoke test — first real end-to-end verification (same day)

Everything until now was static (`analyze` / `test` / `build`) — proof that the
app *compiles*, not that a single request works. Added
**`test/live_api_smoke.dart`**, deliberately **not** named `*_test.dart` so
`flutter test` does not discover it and the offline suite stays deterministic.

```bash
NO_PROXY="localhost,127.0.0.1,::1" flutter test test/live_api_smoke.dart
```

It drives the real repositories against the real backend and **prints** decoded
values (so a run doubles as documentation). **10/10 pass.**

### What it proved
- `fetchCategories()` → 2 categories; `name`→`title`, `icon`→`image`, `slug`,
  `isRoot` all map correctly off real data.
- `fetchCategoryTree()` → 1 root with `children=1` — nesting works.
- `fetchFeaturedCategories()` → envelope unwrapped, 1 item.
- `fetchActiveHero()` → real `media.dl.mceiran.website` url.
- `fetchCourses()` → 500 becomes `ApiException(type: server, message: خطای سرور
  داخلی)`, no crash; `RemoteLoader` keeps the seed (`isRemote: false`).
- `RemoteLoader` on an empty page keeps the seed.
- **Cache: two calls → one network request, 1 cache entry.** Verified, not assumed.

### Two real bugs it caught (both invisible to analyze/test/build)
1. **`fetchHomeBanners` fell back to an auth-only endpoint.**
   `banners/all_active/` is `security: [{jwtAuth: []}]` = **auth required**,
   while `by_type`, `banners/` and `hero/active/` are `[{jwtAuth: []}, {}]` =
   **public** (the bare `{}` is the no-auth alternative). So a **guest** opening
   the home screen took a 401. Fixed: fall back to the public `banners/`.
   Added `fetchBanners()`; documented that `fetchActiveBanners` is auth-only.

2. **Any 401 cleared the session.** `ApiClient`'s interceptor called
   `onUnauthorized` unconditionally, so a guest hitting any auth-only endpoint
   wiped the session + response cache. Fixed: only clear when a token was
   actually sent —
   `if (response.requestOptions.headers['Authorization'] is String s && s.isNotEmpty)`.

### Reusable facts
- **DRF `security` array decodes auth requirements:** `[{jwtAuth: []}, {}]` =
  optional, `[{jwtAuth: []}]` = required. Invisible in the Swagger UI.
- `slug` values are Persian (e.g. `کیک-های-خامه-ای`), not latin — fine as a
  String, but never put one in a URL without encoding.
- Public without a token: `banners/hero/active/`, `banners/by_type/`,
  `banners/`, `courses/categories/` (+ `featured/`, `tree/`), `courses/tags/`.
- Auth required: `banners/all_active/`, `courses/`, `accounts/teachers/`,
  `content/explore-videos/`, `support/*`, `payments/*`.

### Lesson 4
`analyze` + `test` + `build` green means *compiles*, not *works*. A live smoke
test named outside `*_test.dart` gets real end-to-end proof without making the
normal suite network-dependent. Both bugs found here were unreachable by static
checks.

## Auth flow audit — the existence probe (same day)

Went after the user's #1 requirement (phone → OTP vs phone → password), the one
flow never verified end-to-end.

### Confirmed: no dedicated existence endpoint
Enumerated the entire auth surface from the schema — exactly six endpoints:
`send-otp`, `verify-otp`, `login-password`, `reset-password` (PUBLIC) and
`change-password`, `logout` (auth). **Nothing like `check-phone/` exists.**

`SendOTP` = `{phone_number (required), purpose}` — **no check-only flag**. So the
probe's 200 branch genuinely sends an SMS.

### Product issue worth flagging to the owner
Because the probe is `send-otp(purpose=forgot_password)`, **a user who already
has an account receives an SMS the moment they tap «ادامه» on the login screen**
— before choosing anything, when all they wanted was the password screen. This is
inherent to the API, not a coding bug. Mitigations already in place:
- `_AccountProbeCache` — 12 h per phone per device, so at most one probe SMS.
- `AuthRepository.hasFreshOtp` — reuses an OTP sent < 3 min ago, so «ورود با کد
  تایید» is free right after the probe.

Alternatives if the cost/surprise matters: (a) ask the backend for
`accounts/auth/check-phone/`, or (b) probe `login-password` with a dummy password
(lock-out risk). Either way only `AuthRepository.checkAccountExists` changes.

### Verified correct (and now tested)
`checkAccountExists` catches `ApiException`, returns `exists:false` **only** when
`isUnknownPhone`, and **rethrows everything else**. That is the right shape: a
malformed number also answers 400 but with
`یک شماره تماس معتبر وارد نمایید.`, and treating that as "no account" would send
a typo down the new-user → OTP → complete-profile path instead of showing a
validation error.

`isUnknownPhone` requires `statusCode == 400` **and** the text `یافت نشد` or
`وجود ندارد` — so the invalid-format sentence matches neither and the 404
`شناسه پرداخت یافت نشد` is excluded by the status guard.

Added 4 tests (66 total): both phrasings, plus the two negatives — the
invalid-format 400 and the 404. The negative cases were the gap.

## ⚠️ Server media not rendering — ROOT CAUSE: broken TLS cert (same day)

User reported: "media from the server isn't visible in the app."

**The media CDN serves a certificate that does not cover its own hostname:**

```
media.dl.mceiran.website → subject=CN=alvand.irandns.com
                           SAN: DNS:alvand.irandns.com     ← only this
api.mceiran.website      → subject=CN=*.mceiran.website
                           SAN: *.mceiran.website, mceiran.website, www.api.mceiran.website
```

`media.dl.mceiran.website` is **absent from the SAN list** → every HTTPS client
rejects it with a hostname mismatch (`HandshakeException: Handshake error in
client`). Confirmed in Flutter: strict TLS throws; with verification skipped the
same URL returns `200 image/png` and a **complete 24223-byte PNG** — so the files
are fine, only the certificate is wrong.

**This is server-side, not a Flutter bug.** Every URL the backend returns is on
that host (category icons, hero, banners), so *all* server media is invisible.

No app-side workaround exists that keeps TLS intact: `api.mceiran.website/media/…`
→ 404, `media.mceiran.website` doesn't resolve, `mceiran.website/media/…` → 404.

### Fix (server-side)
Issue a cert whose SAN includes `media.dl.mceiran.website`, or serve media from a
host the `*.mceiran.website` wildcard already covers.

### Temporary, opt-in workaround shipped
- `lib/core/network/media_host_overrides.dart` — `MediaHostHttpOverrides`.
- `AppConfig.allowInsecureMediaHost` — **default `false`**.
- `main()` installs it only when the flag is on.
- `badCertificateCallback` returns true **only** for the media host; API, payments
  and the VPN probe keep full validation (the JWT is never exposed).
- Debug builds log what was accepted so it can't be forgotten silently.
- Tests: `LIVE media host TLS` group in `test/live_api_smoke.dart` proves the
  strict failure AND that the override returns 200/24223 bytes, and that
  `allowedHost` is the media host and not the API host.

### Why the app showed nothing rather than crashing
All 26 `Image.network` calls in `lib/pages` already have a matching `errorBuilder`
(verified: net==err for every file), so failed images render placeholders. **No
widget refactor was needed** — the app was already correct.

### Backend is being populated live
Between two runs the DB gained content: categories 2 → 3, a `home_top` banner
appeared (title «یزدان», image a `.webp` on the media host). So live assertions
must not assume emptiness — assert on mapping, not counts. `courses/` still 500s.

### Verification
- `flutter analyze` → 0 errors, 0 warnings
- `flutter test` → **66/66 pass**
- `flutter test test/live_api_smoke.dart` → **13/13 pass**
- `flutter build apk --debug` → built successfully

### Lesson 5
When "server images don't render", check the **TLS certificate SAN list** before
touching a line of app code. `openssl s_client … | openssl x509 -noout -subject
-ext subjectAltName` on both the API host and the media host answers it in
seconds. A hostname mismatch is invisible in the app's own logs — `Image.network`
just reports a generic load failure.

## Media fix shipped (user asked to fix ONLY this, no UI/UX changes)

### Gotcha discovered: never mix testWidgets with live network tests
`testWidgets` initialises the widget binding, which installs an `HttpOverrides`
that blocks real HTTP for the **entire file**. Putting one `testWidgets` in

Fix: keep `testWidgets` in a separate file — hence `test/live_media_image.dart`.

Also inside `testWidgets`, real socket work only completes within
`tester.runAsync(() async { … })`; outside it the fake-async zone never lets the
future resolve.
