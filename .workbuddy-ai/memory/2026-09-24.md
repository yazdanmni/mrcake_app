### EnrollmentStore (new) — the non-obvious bit

OpenAPI path list: no POST anywhere). The only write path is
`POST v1/payments/orders/`. So the API can lag behind, and the profile would show
an empty «دوره‌های من» right after a successful purchase.

Every registration is therefore written **twice**:
1. `POST v1/payments/orders/` (the API record),
2. `EnrollmentStore` — SharedPreferences mirror at `mr_cake.enrollments.local`.

`ProfileMyCoursesSection` merges both, **API wins** on conflict, and passes the
mirror as `RemoteLoader.list(seed: ...)` so it also survives a failed/empty page.
Cleared on logout and on account switch (`SessionManager.clear()` / `.save()`).

### 3. ⚠️ Harness gotcha worth remembering — Persian text + `flutter test`
The test font has no Persian glyphs, so each character renders as a square of
`fontSize`. Copy that fits on a device measures far wider, and full production
screens report `RenderFlex overflowed` that no real user ever sees. The resulting
failure reads *"Multiple exceptions (3) were detected … at least one was
unexpected"*, not an `expect()` failure — easy to misdiagnose.

**The filter must be installed inside the test body, NOT in `setUp`.** `testWidgets`
installs the binding's own `FlutterError.onError` when the body starts, so a
handler set in `setUp` is overwritten before the first pump:

```dart
void ignoreTestFontOverflow() {
  final void Function(FlutterErrorDetails)? original = FlutterError.onError;
  FlutterError.onError = (FlutterErrorDetails details) {
    if ('${details.exception}'.contains('overflowed by')) return;
    original?.call(details);
  };
  addTearDown(() => FlutterError.onError = original);
}
```

Note: enlarging `tester.view.physicalSize` does **not** help — `ScreenUtilInit`
scales the layout and the text by the same factor, so the relative overflow is
unchanged.

## Paid registration is now a REQUEST (ticket + cart), not a payment

### The rule the user settled on (asked, not guessed)
Two readings of their spec were possible, so I asked. Answer:
**«فقط تیکت + سبد خرید»** — no online payment at all — and **build a real cart
screen**. The app must never charge a paid course again.

| Outcome | What happens |
|---|---|
| free course / **100 % coupon** | unchanged free flow → order → `EnrollmentStore` → «دوره‌های من» immediately |
| paid (partial coupon, no coupon, invalid coupon) | **ticket** filed on the user's behalf + course parked in the **cart**; nothing charged, not a student yet |
| admin approves | backend creates the Enrollment → profile picks it up → the cart row disappears on its own |

### The ticket is written by the app
`_submitEnrollmentRequest` in `course_details_screen.dart`:
- `title` = `ثبت نام دوره «<course>» — <first name> <last name>` (≤250, the API cap).
  **The name is in the title on purpose** — `TicketList`, the only payload the
  tickets screen reads, carries `title`/`subject`/`status` and nothing else.
- `message` = name / family name / phone / course / price / coupon / discount /
  final amount.
- `priority` = `high`.
- `subject_id` resolved **by name**, never by id. Live subjects:
  `1 خرید دوره های جدید` ← the right one, `2 مشکل در خرید دوره ها`,
  `3 خرید های قبل`, `4 درخواست دوره های قبلی خودتان`. The endpoint returns them
  **newest-first**, so `results.first` would be the worst possible guess.
  Matching folds `\u200c` → space and `ي/ك` → `ی/ک`.

### `CartStore` (new) — same rationale as `EnrollmentStore`
`POST v1/payments/cart/` is declared in the schema with **no request body and no
response body**, and `GET` is public returning `{items, total_items,
unique_courses, subtotal, total}` — a **single object, not a DRF page**. So
`PagedResult.from` would have produced a cart with one meaningless row;
`CartSummary` replaces it. The POST cannot be verified, so the row is mirrored
locally (`mr_cake.cart.local`) and merged with the API (API wins). `reconcile()`
drops a local row when the server starts returning it **or** when the course
became an enrollment — that second rule is the whole "after approval" behaviour.

## Promo banner carousel — 3s autoplay (and the bug that stopped it)

User: *"یه قسمت بنر داره برای تبلیغاته که اسلایدی هم هست این بنر ها هر 3 ثانیه
خودکار باید ورق بخوره"*.

`HomeBanner` already had an autoplay, but it **could never run on a device**:
`_startAutoPlay()` was called once from `initState`, where `widget.banners` is
still `const []` (the home screen mounts it empty and fills it when
`banners/by_type/?type=home_top` answers), so the `length < 2` guard tripped and
the timer was never re-armed. It only ever worked in tests, where banners are
passed up front — which is exactly why nothing caught it.

Fix:
- `didUpdateWidget` re-arms whenever `!identical(widget.banners, oldWidget.banners)`
  (and clamps `_currentPage` if the list shrinks).
- Interval 4s → **3s**.
- **Single-shot `Timer`, re-armed from `onPageChanged`** — not `Timer.periodic` —
  so a slide the user swiped to by hand also gets its full 3s instead of being
  yanked away mid-read.
- `_advance()` guards on `mounted` **and** `_controller.hasClients`, and re-arms
  even when it cannot advance, so the loop can never die silently.
- `dispose()` still cancels (this is what keeps `flutter test` free of the
  "A Timer is still pending after the widget tree was disposed" failure).

Tests — `test/banner_links_test.dart` → `HomeBanner autoplay` (5): advances every

## Home quick actions: responsive, wired, + students screen & recipes filter

Request: «home quick action» buttons show a pixel-overflow error on some phone
sizes; fix without touching the UI/UX; «هنرجوها» must open a students screen and
«رسپی‌ها» a recipes screen; the recipes screen must show **only** recipes that
belong to no course; those screens must be responsive too; and a screen that is
*both* a navigation tab and a button target must show a back button **only when
it was entered from a button** — «مثل صفحه دوره ها».

### The overflow — `.sp` follows the screen WIDTH, `.h` follows the height

`_QuickActionItem` had `Ink(height: 85.h, width: 85.w)` inside an `Expanded`, with
the icon circle at `37.w` and the label at `16.sp`.

**The root cause is not what it looks like.** `.sp` should be
`min(scaleWidth, scaleHeight)` because `main.dart` sets `minTextAdapt: true` — but
`ScreenUtil.setSp` is

```dart
double setSp(num fontSize) =>
    fontSizeResolver?.call(fontSize, _instance) ?? fontSize * scaleText;
```

and **`ScreenUtilInit.fontSizeResolver` defaults to `FontSizeResolvers.width`**,
which returns `fontSize * scaleWidth` and bypasses `scaleText` completely. Probed
on a 1024×768 surface: `ScreenUtil().scaleText` = `0.910` while `16.sp` = `42.01`
(= `16 × 1024/390`). **So every `.sp` in this app grows with the screen width**,
while every `.h` grows with the height. That single fact explains the whole bug
class; `minTextAdapt` is a red herring here.

Original code, measured with the **real** fonts:

| device | result |
|---|---|
| Galaxy **360×640** | `RenderFlex overflowed by 6.7 pixels` ← the reported phone |
| iPad mini 768×1024 | 38px |
| tablet landscape 1024×768 | 52px |
| iPhone 13 390×844 (design) | none |

Note the earlier session's conclusion (test at 768/1024/landscape) was
**incomplete**: a 360-wide phone overflows too, and that is the one the user
actually had. A 390-wide test device hides it.

Fix (`home_quick_actions.dart`), in order of how long each took to find:

1. drop the fixed `width` (the `Expanded` decides it — a fixed width inside an
   `Expanded` is always a smell);
2. `labelSize = min(16.sp, contentHeight * 0.20)` — cap the text against the card,
   because `.sp` follows the width;
3. **`Ink` applies the decoration's BORDER AS PADDING to its child** — an extra
   `Padding(EdgeInsets.all(2.w))`. So the real content box is
   `height - 2*(paddingV + border)`, not `height - 2*paddingV`. Missing this made
   the reservation short by exactly the border.
4. reserve the label's line box as
   `MediaQuery.textScalerOf(context).scale(labelSize) * 1.25` — a font paints a
   line box a little taller than `fontSize * height` (Shabnam: 18.0 where
   `16 * 1.1` predicts 17.6) and the engine rounds line heights to whole pixels;
5. `iconBox = clamp(min(37.w, contentHeight - gap - labelHeight))`;
6. `Flexible` around the label as the last line of defence — without it a short
   reservation **clips the glyphs silently** instead of raising anything.

At the design size `37.w` is still the smaller term → the card is pixel-identical
(asserted: 37 circle, 22 icon, 85-tall card spanning 25→365). Row gap `8 : 10` →
`8.w : 10.w` (still `8` at the design size).

**Test-harness breakthrough:** `flutter test` does not load the pubspec fonts, so
Persian glyphs render as squares — which had been *hiding* the 360px overflow. New
`test/support/app_fonts.dart` registers the bundled TTFs with `FontLoader`
(10 family spellings: `Shabnam`/`shabnam`, `BShabnam`/`bShabnam`/`bshabnam`,
`pinarb`/`PinarB`/`Pinar`, `pinarr`, `lshabnam`). Do **not** keep swallowing
`overflowed by` in `FlutterError.onError`: it also swallows the real overflow, and
since `tester.takeException()` only sees what that handler forwarded, the
assertion becomes vacuous — two of my own test files had that bug and were fixed.

### Recipes: only standalone recipes

### The `teacher` query param was a real bug

`fetchTeacherPortfolio` sent `query: {'page': page, 'teacher': teacherId}`. With
`teacherId == null` **Dio serialises a null value as a bare key**, so the request
went out as:

```
https://api.mceiran.website/api/v1/content/teacher-portfolio/?page=1&teacher
```

No `=`, no value. DRF answers an empty integer filter with a **400**, so the
across-every-teacher gallery would have been blank on the device while the teacher
profile (which always passes a real id) looked fine. Now `'teacher': ?teacherId` —
the null-aware marker drops the entry entirely. Found because a test asserted the
key was *absent* and failed with `Expected: false / Actual: <true>`; the Dio log
in the failure output showed the bare `&teacher`.

### The player needed to cope with images

`ReelsViewer` speaks `ExploreVideo` and `_ReelItem` treated an empty `videoUrl` as
`آدرس ویدیو خالی است.` — but `TeacherPortfolioItem.type` is `image` | `video`, so
half the gallery would have opened on an error screen. `_ReelItem` gained an
**image mode**: empty url *with* a thumbnail → full-bleed still, no player, no
play/pause, no progress bar. Additive: Explore's items always carry a url.

The instructor chip (`«استاد {lastName}»`) is now hidden when both names are empty,
and the `12.h` gap moved inside the same conditional.

`TeacherPortfolioViewer.teacher` was briefly made nullable for this screen; when
the screen switched to `ReelsViewer` that flexibility became dead, so it was
reverted to `required Teacher`.

### «رسپی‌ها» empty state

`_buildRecipesGrid` returned a two-column `SliverGrid` holding one

### Both media types (round D-4)

Final ask: *«قسمت پروفایل استاد توی نمونه کارها میتونه هم ویدیو باشه و هم عکس و

**Nothing structural was missing.** The students page renders the teacher profile's
own `TeacherPortfolioGrid` → `TeacherPortfolioItemCard`, and the endpoint already
returns `type: image | video` rows. So "same structure" was already true; what was
missing was coverage and one honest asymmetry.

* The badge is **type-driven**: `TeacherPortfolioItemCard` paints its
  `play_arrow_rounded` disc inside `if (item.isVideo)`, and
  `isVideo = Json.asString(json['type']) == 'video'`. An image work can never be
  badged.
* ⚠️ **A video work has no cover image.** The real payload is
  `{id, type, description, position, is_published, teacher, media}` — **no cover
  field at all**. `image` is parsed from

  row has, so the resolved url *is* the video, `image` stays empty, and the card
  paints its badge over the `Icons.image_outlined` **placeholder**. Image and video
  are **not symmetric**. This is identical on the teacher profile (same widget,
  same payload) — "fixing" it here would diverge the two screens, which is exactly
  what the request forbade. A real poster frame needs a backend field, not a client
  change.
* The player handles both via `_ReelItem`'s image mode: `videoUrl: item.videoUrl ?? ''`
  and the empty-url + non-empty-thumbnail branch.
